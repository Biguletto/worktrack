# WorkTrack Demo Edition - Limitations to Disclose

These are intentional class-demo limitations. Do not present them as completed production controls.

| Revision item | Current limitation | Suggested presentation wording |
|---|---|---|
| 2. Username-only login lockout | Failed-login lockout is keyed only by username for a one-hour cool-off. This avoids relying on a forwarded client IP, but anyone who knows an account name can intentionally lock that account temporarily. | "The demo locks a username after repeated failed logins. This reduces dependence on client IP headers, but a known username can be temporarily locked; production should add monitoring and a recovery procedure." |
| 15. Daily QR credential duration | A user's QR is unique to that employee and Manila calendar day, but remains the same throughout that day. It can be screenshotted or shared. | "For the class demo, the Administrator visually checks the person presenting the QR. A production enhancement would rotate the QR credential every 30-60 seconds." |
| 16. Attendance correction request | Attendance records are read-only to Administrator under the current policy, and there is no employee missed-scan correction request workflow. A future release could add a supervisor/HR review workflow for correction requests, while retaining the Administrator read-only policy. | "Employees currently report a missed scan outside the system. A future release could add a request reviewed by the supervisor and HR, with the approved correction handled through a separately controlled HR workflow." |
| 17. Fixed leave catalogue | The application starts with VL, SL, EL, PL, and LWOP. HR cannot edit the catalogue. Statutory leave categories such as maternity, paternity, and solo-parent leave are not modeled; paid and balance flags are starter configuration values, not company policy. | "The five categories are demonstration defaults. A real rollout requires HR/legal review of leave categories, entitlements, documentation, and balances." |
| 18. Availability and failover | The baseline uses one EC2 instance and one RDS instance. It has no application failover or multi-AZ database. The second private subnet is present for the RDS subnet group requirement, not as an active failover deployment. | "This is a small single-instance demonstration architecture, not a high-availability design." |
| 19. Monitoring and alerting | The application includes an Administrator System Logs page and logs are available through `journalctl`; CloudWatch alarms and automated log retention are not configured. The application event table has no retention limit. | "The demo uses application and service logs for basic troubleshooting. Production requires CloudWatch alarms, retention rules, and log review." |
| 20. Antivirus scanning | Uploads are checked by extension, size, and file signature. No antivirus or malware-content scanning step is included. | "The current checks are basic file validation, not malware protection. Production should scan uploaded documents before storage or access." |
| 21. Performance/load testing | The deployment is sized for a small number of demonstration users on small EC2/RDS instances. No load or performance test has been completed. | "The prototype has only been checked functionally; user-volume capacity is not yet measured." |
| 22. HTTP without TLS | HTTP is acceptable only for dummy data through the local SSH tunnel or a tightly restricted demonstration setup. Public plain HTTP must not carry real credentials or employee information. | "The kiosk camera uses localhost through an SSH tunnel for the demo. Public use requires valid HTTPS and secure-cookie settings." |
| 23. Dummy data and privacy | Demo records must be fictional. Employee files, medical certificates, and employment data are sensitive under the Data Privacy Act of 2012 (RA 10173). A real deployment requires privacy, lawful-purpose, retention, access, and incident-response review. | "We use fictional sample data. A real organization must complete privacy and retention review before onboarding employees." |
| 24. Large views module | `eqrApp/views.py` remains a large single module (about 1,500 lines in the reviewed build). | "The current implementation keeps views in one module to simplify the class demo. A maintainability refactor would split accounts, attendance, kiosk, leave, and admin/system views." |

## Additional operational caveats

- A daily QR scan is not biometric identity verification. The QR contains a signed credential, not proof of who is physically holding the phone.
- The ZXing library is loaded from a CDN. Confirm classroom network access to jsDelivr and unpkg. The main scanner has no manual QR-token field or manual attendance fallback. If the camera cannot be used, restore camera/network access or use a pretested backup kiosk device.
- Camera access requires localhost or HTTPS. For a remote EC2 class demo, use the documented SSH port-forward and open `http://localhost:8000` on the kiosk laptop.
- The demo email backend writes messages to service output. It does not deliver mail.
- AWS credits and trial eligibility are account-specific and time-limited. Do not describe the AWS architecture as permanently free or assume costs are zero.
- The ZIP does not prove that CloudFormation, EC2, RDS, S3, Session Manager, TLS, SMTP, or a real camera has been deployed/tested. Demonstrate only what has actually been run in the group's environment.
